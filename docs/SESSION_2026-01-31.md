## Data Flow

### Budget Planning Flow
```
User → Plan Page
  ↓
  Sets Expected Income (85,000 Kč)
  Sets Investment Target (10,000 Kč)
  ↓
  Adds Category Budgets:
    - Food & Dining: 10,000 Kč
    - Transportation: 6,000 Kč
    - Entertainment: 5,000 Kč
  ↓
  Summary Calculation:
    Income:      85,000 Kč
    - Budgeted: -21,000 Kč
    - Invest:   -10,000 Kč
    = Remaining: 54,000 Kč
```

### Spending Tracking Flow
```
Transactions in DB (expenses with categories)
  ↓
  Plan Service queries current month transactions
  ↓
  Groups spending by category
  ↓
  Matches with budgets
  ↓
  Calculates percentage spent
  ↓
  Displays in progress bars
```

## Key Design Decisions

### 1. Why Client-Side Plan Page?
- **Immediate Feedback**: No page reload when editing values
- **Interactive**: Inline editing feels responsive
- **State Management**: Easy to manage with React hooks

### 2. Why Separate Cards for Income/Investment?
- **Clear Separation**: Different purposes, different cards
- **Reusable Pattern**: Same inline editing pattern
- **Visual Hierarchy**: Two cards side-by-side on desktop

### 3. Why Progress Bar Extends Past 100%?
- **Visual Feedback**: User sees they've overspent
- **Color Change**: Red indicates problem
- **No Hard Limit**: Bar doesn't stop at 100%, shows actual overage

### 4. Why Keep Accounts Table?
- **Legacy Data**: Preserve historical data
- **Backwards Compatibility**: Income table still has account_id
- **Future Options**: Could re-enable later if needed

### 5. Why Service Layer Pattern?
- **Separation of Concerns**: UI doesn't know DB structure
- **Reusability**: Same service across components
- **Type Safety**: Consistent error handling
- **Testability**: Services can be unit tested
